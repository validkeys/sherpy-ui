# Comprehensive Code Review — sherpy-ui
Date: 2026-05-06  
Stack: React 19 · TanStack Start · TanStack Router · React Query · Tailwind v4 · Biome · Vitest

## Critical

### `app/routes/__root.tsx:11` — QueryClient created at module scope
```ts
const queryClient = new QueryClient(); // module-level singleton
```
In SSR, this QueryClient instance is shared across all concurrent requests. React Query's cache bleeds between requests: user A's data can appear in user B's response. Must move instantiation inside `RootComponent` or use a factory with `useState`:
```ts
function RootComponent() {
  const [queryClient] = useState(() => new QueryClient());
  ...
}
```

### `src/features/projects/store.ts:4` — In-memory store incompatible with serverless
```ts
const store = new Map<string, Project>();
```
Vercel spins up new function instances on cold starts and can run multiple instances in parallel. Each has its own `Map`. Creates, updates, and list queries won't be consistent across instances. Codes generated by `counterRef` will collide across instances (both can issue `SHR-0042`). Acceptable for M1 demo; must be replaced with a real store before any multi-user use.

### `src/features/projects/store.ts:58-61` — Top-level `await` side effect on module import
```ts
if (process.env.SEED_DATA !== "false") {
  const { seedStore } = await import("./seed");
  seedStore(store, counterRef);
}
```
Top-level await is valid ESM, but running a side effect (seeding) at import time means:
- Any module that imports from `store.ts` triggers seeding
- In test environments, `_resetStore()` clears seed data, but import order matters
- Seeding in `store.test.ts` is cleared by `beforeEach(_resetStore)` — correct, but fragile if import order changes
Consider extracting seed to an explicit init call.

## Major

### `app/routes/dashboard.tsx:20-24` — `onCreated` callback is never handled
```tsx
<CreateProjectFlow
  open={createOpen}
  onClose={() => setCreateOpen(false)}
  // onCreated is optional — never passed here
/>
```
`CreateProjectFlow.onCreated` receives the new project id but nothing navigates to it. After creation, user returns to the list. If navigation to a project route is intended, this is a silent gap.

### `src/components/left-rail/LeftRailNav.tsx:25-40` — Project buttons don't navigate
```tsx
<button key={project.id} type="button" ...>
  {project.name}
</button>
```
No `onClick` handler. The active state check (`isActive`) reads `location.pathname` correctly, but clicking a project does nothing. Should be `<Link to="/project/$id">` from TanStack Router, or at minimum call a passed callback.

### `src/features/projects/hooks.ts` — No error handling on mutations
Both `useCreateProject` and `useUpdateProjectStatus` have no `onError`. Failed server calls produce zero user-visible feedback. A network error or validation throw is silently swallowed. Minimally add `onError` to surface errors to the UI, or document that callers are responsible.

### `src/features/projects/components/ProjectList.tsx:14` — Missing error state
```ts
const { data: projects, isLoading } = useProjects();
```
`isError` is destructured nowhere. If `$listProjects` throws (server down, serialization error), the component renders the "No active projects" empty state. This will confuse users. Add:
```tsx
const { data: projects, isLoading, isError } = useProjects();
// ...
if (isError) return <ErrorState />;
```

### `src/components/intake/CreateProjectFlow.tsx:59-135` — Custom modal missing a11y primitives
The overlay `div` lacks:
- `role="dialog"` and `aria-modal="true"`
- `aria-labelledby` pointing to the title
- Focus trap (tabbing out of the modal)
- Escape key handler to close

With `@base-ui/react` already installed, use `Dialog.Root` / `Dialog.Popup` instead of the hand-rolled overlay.

## Minor

### `src/components/intake/PathCard.tsx:19-23` — `div[role="button"]` instead of `<button>`
```tsx
<div role="button" tabIndex={0} onClick={onClick}
  onKeyDown={(e) => (e.key === "Enter" || e.key === " ") && onClick?.()}>
```
Two problems:
1. `Space` keydown doesn't call `e.preventDefault()` — fires scroll on the page before calling `onClick`.
2. Browsers don't give divs the same implicit ARIA semantics as native buttons (cursor, touch target, etc.).

Use `<button type="button">` and remove the manual `role`/`tabIndex`/`onKeyDown`.

Note: `biome.json:26` has `"useSemanticElements": "off"` — this rule would have caught the issue. Reconsider disabling it.

### `src/components/left-rail/LeftRail.tsx:47-51` — Hardcoded real user PII
```ts
const DEFAULT_USER: UserInfo = {
  initials: "KW",
  name: "Kyle Welsby",
  handle: "@validkeys",
};
```
Real name/handle committed to source. Fine for a local demo but will appear in any future OSS release or screenshot. Replace with `"Demo User"` / `"@demo"` for the default.

### `src/features/projects/components/ProjectCard.tsx:70-89` — Inaccessible action buttons
Archive and Complete buttons have no context about which project they act on. Screen reader announces "Archive" without knowing which project. Add `aria-label`:
```tsx
<button aria-label={`Archive ${project.name}`} ...>Archive</button>
<button aria-label={`Complete ${project.name}`} ...>Complete</button>
```

### `src/features/projects/server.ts:19` — No max-length on project name
```ts
if (typeof d.name !== "string" || !d.name.trim())
```
No upper bound. A 10MB string passes validation, gets stored, serialized in every `listProjects` response. Add `d.name.length > 120` guard.

### `src/features/projects/server.test.ts:17-39` — Validator logic duplicated in tests
The `validateCreateProjectInput` and `validateUpdateStatusInput` helpers in `server.test.ts` are copy-pastes of the logic inside `server.ts`. If server validators change, tests keep passing against the old copy. Extract validators to a separate module, or test them via the server fn directly once the TanStack Start plugin constraint is resolved.

### `src/features/projects/components/ProjectCard.tsx:11-22` — `STEP_LABELS` has no type safety
```ts
const STEP_LABELS: Record<number, string> = { 1: "Intake", ... 10: "Review & Finalize" };
```
`currentStep` is `number` with no range constraint on the type. `STEP_LABELS[project.currentStep] ?? "Unknown"` silently falls to "Unknown" for out-of-range steps. Consider a union type for `currentStep` (1–10) or at minimum log a warning on unknown steps during development.

### `src/components/mode-toggle/ModeToggle.tsx:2` — `useEffectEvent` is experimental
```ts
import { useEffect, useEffectEvent } from "react";
```
`useEffectEvent` is still in React's experimental/canary channel as of React 19.x stable. It isn't in the stable TypeScript types. This works because `tsconfig.app.json` has `"ignoreDeprecations": "6.0"` and `skipLibCheck: true`, masking the type error. Track the React RFC for when this stabilizes; the implementation is correct but fragile if React types change.

### `src/features/projects/seed.ts:49` — `counterRef` reset may collide with seed codes
```ts
counterRef.value = Math.max(counterRef.value, 5);
```
Seed codes go up to `SHR-0004`, so counter advances past 4 to 5. But `store.ts:5` initializes `counterRef.value = 42` and `nextCode()` starts at SHR-0042. The `Math.max(42, 5) = 42`, so seed correctly leaves the counter at 42. This is fine. However, if `_resetStore()` resets the counter to 42 and seed is not re-run, new projects start at SHR-0042 while seed codes (SHR-0001–SHR-0004) already exist. No collision, but the gap (SHR-0005 through SHR-0041) is never issued. Minor cosmetic oddity.

## Architecture / Design Observations

**Dual `useProjects()` subscriptions**: Both `LeftRailNav` and `ProjectList` call `useProjects()` independently. React Query deduplicates the fetch, so no double request. This is fine and idiomatic.

**`updateProjectStatus` can't restore**: `$updateProjectStatus` only allows `"archived" | "complete"`. There's no path back to `"active"`. Likely intentional; ensure product spec agrees.

**`dashboard.tsx` grid hardcodes `240px` left-rail width**: `grid-cols-[240px_1fr]`. If `LeftRail` width changes (e.g. for mobile), the layout breaks. Consider a CSS variable or a Tailwind config value so both agree.

**Route tree only has two routes**: `/` (redirect) and `/dashboard`. The `LeftRailNav` checks for `/project/${project.id}` but no such route exists. This means the active-state logic in `LeftRailNav` will never be truthy and can be removed until that route is built.

**No Suspense boundaries**: The app uses React Query for async data but has no `<Suspense>` boundaries. `isLoading` checks in individual components work, but adding a Suspense boundary at the route level would clean up loading state handling and enable future use of `useSuspenseQuery`.
